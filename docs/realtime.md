# LCD 1.22 实时绘图调查

调查对象：RTX 3070 Ti Vulcan 的 LCD 3.0；本机固件字符串 122。
固件样本 SHA-256：2B3AC75798C06945CCD6CAF7A792248C6E8B7D4AEFA0A46638E5F59BA421A429。

## 结论和证据边界

1. **状态联动已可实现，置信度高。** 动画一次上传到屏幕存储，再按任务事件切换。2026-10-07 实测 Codex、助手 B 的六段动画均能通过小工具接受播放指令，并恢复 img2.savi。软件回执和文件目录均验证过，物理屏幕画面仍需人眼确认。
2. **厂家库没有发现“任意 RGB/JPEG 帧直接送到屏幕内存”的接口，置信度高，仅限这份 DLL。** 本次枚举了 ILCD3、LCD3、LCD3Core 的公开和非公开方法及命令枚举。可见的是文件上传、文件播放、文字、固定监控页面、设置、维护模式。
3. **在已追踪的 1.22 固件主命令分发中，没有找到独立的帧提交指令，置信度中等。** 这不是证明整个固件绝对不存在隐藏入口；没有完成所有中断、USB 类请求、第二核渲染路径的完整反编译，也没有进行未知指令扫描。
4. **自定义文字的位置、颜色和内容存在协议支持，置信度中高。** 不是自由像素画布。固件对 X/Y 分别限制到 479/127，并处理多段文本。SDK 数据模型也有 X、Y、字体、颜色、移动方式和三行文字。可以继续探索“静态背景 + 低频文本/数值”的仪表板，但本轮没有在硬件上做持续刷新压力测试。
5. **通过不停上传 SAVI 来模拟实时视频不合适。** 实测约 99–101 KB 的上传数据阶段为 405–448 ms，另外还有模式切换、确认与文件操作；全流程更慢。当前接口确实写文件。不能把“USB 物理带宽足够”推断为固件有现成的视频接收能力。

文件传输分支调用文件写入例程，不能把 E41B 的 “WriteData” 名称当成写帧缓冲。
文字分支在 0x1001A8C6–0x1001A8E6 限制 X/Y；数据页分支解析日期和数值字段。
汇编由 Capstone 5.0.7 生成；线性反汇编中混有常量池，结论只使用从有效分支可追踪的代码段。

## 可以做的玩法

- 已实现：任务开始 / 等待操作 / 回合结束，Codex 与 助手 B 分开控制，灯光共享状态。
- 使用现有能力继续开发：番茄钟、构建/下载结束提醒、模式切换动画、日历或时钟主题、像素宠物预制动画。
- 值得进一步实验：固定背景叠加短文字、低频温度/进度数值更新；需要验证字体编码、刷新稳定性和默认画面恢复。
- 尚未证实：任意桌面画面镜像、任意 SignalRGB 灯效逐帧投屏、实时频谱/自由图形绘制。
- 修改固件原则上属于另一条开发路线：需要先确定双核通信、显示帧缓冲、传输命令、校验及可靠救砖方法。现有发现不足以直接制作可安全刷入的补丁。
